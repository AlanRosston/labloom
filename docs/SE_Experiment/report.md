# 知织（Labloom）课内概念问答准备

用于应对“课内某个概念，在你们项目里是什么”这类提问，不涉及代码。

依据：note/ 前三章笔记；《知织（Labloom）需求规格说明书》1.2（课程实验版）；《知织（Labloom）系统概要设计说明书》0.2。

回答顺序：先用一句话给出定义，再举项目中的例子，最后说明它在哪份文档或哪张图里。

## 0 项目速查（先记熟）

- **一句话**：知织是面向学生科研与课程调研的本地桌面应用，覆盖“获取资料、阅读、记录、查找”的基本流程。
- **参与者**：用户（学生）；订阅来源（外部系统，提供 RSS／Atom 论文动态）。
- **六个用例**：UC01 创建或打开工作区，UC02 管理订阅源，UC03 刷新与阅读订阅，UC04 导入与阅读 PDF，UC05 编辑与保存笔记，UC06 检索资料。
- **分析类（22 个）**：8 个实体类（Workspace 工作区、FeedSource 订阅源、FeedItem 订阅条目、Page 页面、NotePage 笔记页、PaperPage 文献页、Block 内容块、Attachment 附件）；8 个边界类；6 个控制类，每个用例一个。
- **分析模型的图**：用例图；每个用例一张泳道活动图和一张时序图；实体类图和分析类图；笔记页、订阅源两张状态图。
- **概要设计**：六个顶层包，依次为界面表示、接口控制、应用服务、领域模型、数据持久化、平台支撑。
- **当前进度**：需求分析已完成并通过答辩，概要设计为 0.2 初稿。代码目前是原型，已有工作区创建与打开、订阅刷新与已读、PDF 浏览和编辑器原型，尚未完整实现和打包。

## 1 实体类、边界类、控制类（BCE）

**问：三类分析类在项目中分别是什么？**

| 类型 | 一句话 | 我们项目中 |
| --- | --- | --- |
| 实体类 | 保存业务信息（系统里有什么） | Workspace、FeedSource、FeedItem、Page、NotePage、PaperPage、Block、Attachment |
| 边界类 | 负责系统与外界交互（通过什么操作） | 面向用户：WorkspaceUI、SourceUI、FeedUI、PaperUI、NoteUI、SearchUI<br>面向外部系统：FeedGateway（订阅获取接口）、FileDialog（文件选择窗口） |
| 控制类 | 组织一个用例的流程（谁来组织） | WorkspaceController、SourceController、RefreshController、PaperController、NoteController、SearchController |

记法：实体类是名词，如订阅源；边界类是界面或接口，命名为 xxxUI；控制类每个用例一个，命名为 xxxController。规格说明书表3.10（概念类）列出了全部 22 个类。

**问：按用例分别举例。**

| 用例 | 边界类 | 控制类 | 实体类 |
| --- | --- | --- | --- |
| UC01 创建或打开工作区 | WorkspaceUI | WorkspaceController：检查目录，创建或打开 | Workspace |
| UC02 管理订阅源 | SourceUI、FeedGateway | SourceController：查重、校验地址、保存 | FeedSource |
| UC03 刷新与阅读订阅 | FeedUI、FeedGateway | RefreshController：获取、去重、标记已读 | FeedSource、FeedItem |
| UC04 导入与阅读 PDF | PaperUI、FileDialog | PaperController：检查文件，保存附件，创建文献页 | PaperPage、Attachment |
| UC05 编辑与保存笔记 | NoteUI | NoteController：添加文献链接，组织自动保存 | NotePage、Block |
| UC06 检索资料 | SearchUI | SearchController：查询并打开结果 | Page、FeedItem |

**追问：订阅来源已经是参与者，为什么还要有“订阅获取接口”这个边界类？**
参与者位于系统外部，边界类位于系统内部，负责与参与者通信。用户对应各个 xxxUI 界面，订阅来源对应 FeedGateway。

**追问：三类之间怎样协作？**
看任何一张时序图都是同一个顺序：用户 → 边界类 → 控制类 → 实体类，结果再沿原路返回。例如 UC03：用户在 FeedUI 点刷新 → RefreshController 通过 FeedGateway 取回条目 → 调用 FeedItem 的 existsByUrl() 去重、create() 保存。分析类图（图3.9）里的依赖箭头也是这个方向，实体类不依赖边界类和控制类。

**追问：为什么每个用例设一个控制类？**
控制类负责一个用例的流程，一个用例一个控制类，职责清楚，修改某个用例的流程时只改对应的控制器。控制类只组织流程，不保存数据，所以没有属性。

**追问：分析类到了设计阶段对应什么？**
边界类对应界面表示包；控制类对应应用服务包；实体类的业务规则放在领域模型包，存储放在数据持久化包。

**问：需求工程的七项任务，你们分别做了什么？**

| 任务 | 项目中的工作 |

| 协商 | 处理冲突与取舍：AI 改为可选功能；本版不做订阅分组；取消订阅时保留历史条目 |
| 规格说明 | 需求规格说明书（完整版 v4，课程实验版 1.1） |
| 确认 | 9 月 23 日需求分析答辩，规格说明书经批阅后修改，填写评审记录 |
| 管理 | 需求编号（LB-USR、LB-SRS）、用户需求与系统需求对照表、版本修改记录 |

**问：利益相关者有哪些？多重观点体现在哪里？**
学生用户（主要用户）、项目组成员（开发者）、指导教师（评审者）、订阅来源网站（外部系统）。观点冲突的例子：用户希望功能越多越好（任务日程、AI、同步），开发者只有一学期时间。因此我们给需求排了优先级，并做了裁剪。

**问：功能需求、非功能需求和实现决策有什么区别？**

| 类别 | 项目中的例子 |
| --- | --- |
| 功能需求（做什么） | 添加订阅源、刷新订阅、导入 PDF、笔记自动保存、按关键词检索 |
| 非功能需求（做得怎样） | 冷启动不超过 5 秒；搜索首批结果在 1 秒内返回；停止编辑后 1 秒内自动保存；支持 1 万个页面、10 万条订阅条目；资料保存在本地 |
| 实现决策（怎么做） | Electron 桌面框架、Svelte 界面、SQLite 数据库、pdf.js 阅读 PDF |

判断方法：去掉技术名词后仍然成立的是需求，写了具体技术的是实现决策。例如“使用 SQLite”不是需求。

**追问：非功能需求写在哪里？**
写在需求规格说明书第 2.2 节，共 9 项：性能、容量、可用性、保存与可靠性、故障分析、安全性、易用性、可维护性、国际化和本地化。课程 ppt 把非功能需求放在第 2 章“系统概述”；第 3 章分析模型只描述系统做什么，不写非功能需求。

**问：需求获取阶段产出了哪些工作产品？**
可行性说明对应选题介绍中的定位和学期约束；利益相关者列表；需求列表对应 LB-USR；系统环境描述对应应用环境（三个桌面平台，四核 CPU、8 GB 内存和 SSD）；用例和原型对应六个用例及界面布局草图。技术方案不属于这一阶段的工作产品。

**问：讲一个用例的组成，以 UC03 刷新与阅读订阅为例。**
- 参与者：用户（主参与者）、订阅来源
- 前置条件：工作区中已有订阅源
- 基本流程：用户刷新 → 系统获取内容，去重后保存 → 用户打开条目阅读摘要，系统标记为已读 → 用户可打开原文
- 备选／异常流程：抓取失败时显示原因，用户可重新刷新
- 后置条件：新条目和阅读状态已保存

**问：怎样从需求描述中找出类？**
用名词分析。“用户添加来源，填写名称和订阅地址”中，订阅源是类，名称和订阅地址只是它的属性。这和笔记中“课程名称是课程的属性”是同一个道理。

## 3 类图与类关系

**问：类的三层表示，以订阅条目为例。**

| FeedItem 订阅条目 |
| :---: |
| - id、title、url、summary、publishedAt、isRead |
| + create()、existsByUrl()、markRead()、findByKeyword() |

属性用名词，操作用动词。封装：属性全部私有（-），isRead 只能通过 markRead() 修改；控制类里只在内部使用的 checkDirectory()、checkPDF() 也设为私有。

**追问：类的操作是怎么定出来的？**
从时序图中来：发给某个类的每条消息，就是这个类的一个操作。例如时序图中 RefreshController 向 FeedItem 发送 markRead()，FeedItem 就有 markRead()。规格说明书表3.11至表3.13给出带参数类型的完整定义。

**问：五种类关系在类图里分别对应什么？**

| 关系 | 我们类图中的例子 | 说明 |
| --- | --- | --- |
| 关联 | FeedSource 0..1 — 0..* FeedItem；NotePage —引用— PaperPage；PaperPage 1 — 0..* Attachment | 长期保持的联系 |
| 聚合 | Page ◇— Block（正文） | 空心菱形，弱的整体—部分关系 |
| 组合 | Workspace ◆— FeedSource、FeedItem、Page | 实心菱形，部分随整体消失 |
| 泛化 | NotePage、PaperPage → Page（抽象类） | 空心三角；笔记页是一种页面，继承 id、title、tags 和 rename() |
| 依赖 | 边界类 → 控制类 → 实体类（图3.9 的虚线箭头） | 临时使用另一个类的能力 |

**追问：页面和内容块为什么画成聚合，而不是组合？**
同一个内容块可以被多个页面共享（同步块），删除一个页面不一定删除这个块。块的生命周期不由单个页面决定，所以是聚合。

**追问：订阅源和订阅条目为什么不是组合？**
需求规定取消订阅后保留历史条目，条目不随来源一起删除。

**追问：工作区和页面为什么是组合？**
页面、订阅源和订阅条目都保存在工作区里，不能脱离工作区存在；工作区删除后，它们也随之删除。注意订阅条目同时关联订阅源（0..1），但它的“整体”是工作区，所以移除订阅源时条目还在。

**问：关联和依赖怎么区分？**
订阅条目一直记着自己属于哪个订阅源，这是关联。检索时，SearchController 临时调用 Page 的 findByKeyword()，用完后不保存对方，这是依赖。

## 4 行为模型与其他图

**问：讲一下时序图（以 UC05 编辑与保存笔记为例）。**
用户在 NoteUI 编辑 → 停止输入 1 秒后，NoteUI 调用 NoteController 的 saveNote() → 控制器调用 NotePage 的 rename()，再对每个修改过的内容块调用 Block 的 update()（loop 框）→ 调用 NotePage 的 save() → alt 框按结果分两支：成功则界面显示“已保存”，失败则提示并保留内容。实线实心箭头是调用，虚线是返回（return），show 是界面显示给用户。每条调用就是面向对象中的“消息”，也正是接收方类的操作。六个用例各有一张时序图（图3.10至图3.15）。

**问：讲一下状态图。**
画了两张，都是实体类某个属性的取值变化：
- 笔记页 saveStatus（图3.16）：编辑中 →〔停止输入 1 秒／提交保存〕保存中 →〔写入成功〕已保存 →〔继续编辑〕编辑中；保存中 →〔写入失败／保留编辑内容〕保存失败 →〔重试〕保存中。
- 订阅源 status（图3.17）：〔添加，地址有效〕正常 →〔刷新〕刷新中 →〔获取成功／保存新条目〕正常；刷新中 →〔获取失败／显示原因〕抓取失败 →〔重新刷新〕刷新中；正常或抓取失败时可以移除。

箭头上的写法是“事件 [条件] / 动作”，和笔记里咖啡机的例子一致。

**问：顺序图和状态图有什么区别？**
顺序图关注多个对象之间谁先调用谁；状态图关注一个对象自身的状态如何变化。

**问：活动图或泳道图是怎么画的？**
规格说明书为六个用例各画了一张泳道活动图（图3.2至图3.7），泳道为用户、知织，涉及订阅的两张再加订阅来源。菱形是判断，方括号内是分支条件。

举例（UC03）：［用户］点击刷新 → ［知织］向订阅来源请求内容 → ［订阅来源］返回内容 → ［知织］判断是否成功：成功则去重、保存并显示列表；失败则显示原因 → ［用户］可重试。

**问：数据流图怎么画？**
我们没有单独画数据流图，概要设计中有一张“订阅条目到文献阅读的数据流程”图。口头描述如下：
- 外部实体：用户、订阅来源
- 处理：刷新订阅、导入 PDF、保存笔记、检索资料
- 数据存储：工作区数据库、附件目录
- 数据流：订阅地址 → 刷新订阅 → 新条目 → 数据库；关键词 → 检索资料 → 结果列表

## 5 设计概念

**问：以下设计概念在项目中对应什么？**

| 概念 | 项目中的对应 |
| --- | --- |
| 数据抽象 | 用“页面”统一表示笔记和文献，只保留 id、标题、标签等共性 |
| 过程抽象 | “刷新订阅”是一个操作，内部包含下载、解析、去重和保存 |
| 模块化 | 系统分为六个顶层包；需求按订阅、文献、知识库、通用分板块，便于分工 |
| 信息隐藏 | 界面不能直接访问数据库和文件，只能调用 preload（预加载层）暴露的受限接口；数据库连接只在主进程中 |
| 功能内聚 | 订阅模块只负责来源、抓取、条目和阅读状态 |
| 顺序内聚 | 刷新订阅时依次下载、解析、去重、保存，前一步的输出是后一步的输入 |
| 数据耦合 | 界面标记已读时只传条目 id 和“是否已读”两个简单值 |
| 标记耦合 | 把整个订阅条目对象传给列表界面显示 |
| 控制耦合 | 刷新时传入“指定来源／全部来源”参数，决定刷新范围 |
| 降低耦合 | 包之间只允许单向依赖：界面 → 接口 → 服务 → 模型、存储、平台，下层不调用上层 |
| 重构 | 概要设计计划把订阅模块中的数据库操作移入持久化包，并把建表改为版本化迁移；功能不变，结构更清楚 |
| 继承 | 笔记页、文献页继承页面 |
| 多态 | 同样是“打开”操作，笔记页打开编辑器，文献页打开 PDF 阅读器 |
| 消息 | 时序图中的 saveNote()、markRead() 等调用 |

**问：五类设计类分别对应什么？**

| 设计类 | 我们的包 | 例子 |
| --- | --- | --- |
| 用户界面类 | 界面表示包 | 笔记编辑界面、PDF 阅读器、订阅列表 |
| 业务领域类 | 领域模型包 | 页面、内容块、订阅源、订阅条目、附件 |
| 过程类 | 应用服务包 | 工作区会话、订阅服务、文献导入、检索服务 |
| 持久类 | 数据持久化包 | 仓储、事务、数据库迁移 |
| 系统类 | 平台支撑包 | 文件读写、网络请求、日志、系统通知 |

六个包中剩下的接口控制包，负责在界面与主进程之间转发请求、校验参数。注意区分：分析类有 3 类（BCE），设计类有 5 类。

**问：设计模型的各部分分别对应什么？**

| 部分 | 项目中的对应 |
| --- | --- |
| 数据设计 | 每个工作区一个 SQLite 数据库，保存页面、内容块、订阅和附件信息；PDF 文件放在附件目录，数据库只记录文件名 |
| 体系结构设计 | 六个顶层包分层；运行时分为渲染进程（界面）、preload（桥接）和主进程（业务与存储） |
| 接口设计 | 用户接口：主窗口的导航、侧栏、标签页和内容区<br>外部接口：RSS／Atom、文件选择窗口、系统浏览器、系统通知<br>内部接口：preload 暴露的类型化 API |
| 构件级设计 | 尚未开始，属于详细设计 |
| 部署设计 | 单机桌面应用，不需要服务器。包括应用程序、应用数据目录（配置、日志）、工作区目录（数据库、附件），按需联网访问订阅来源 |

分析模型说明“做什么”（六个用例、八个类）；体系结构说明“怎么组织”（六个包）。

| 可复用性管理 | 复用开源组件：pdf.js、Tiptap 编辑器、SQLite |
| 度量 | 性能指标使用 P95，即至少 95% 的样本不超过目标值 |
| 风险管理 | 概要设计第 13 章“尚未解决的问题”，例如中文全文检索效果、跨平台打包 |

**问：你们用的是什么过程模型？**
以迭代增量为主，接近统一过程，并结合了原型：
- 需求先整体分析，实现分为三个增量：① 工作区、页面编辑与保存；② 从订阅到文献阅读；③ 任务提醒、搜索与备份。
- 订阅、PDF 阅读、编辑器都先做原型，再逐步接通。
- 不用瀑布模型，是因为需求一直在变化，规格说明书改过多个版本；不用纯敏捷，是因为课程要求完整的文档。

**问：统一过程（UP）的特点在项目中怎样体现？**
- 用例驱动：六个用例贯穿需求、分析、设计和测试。
- 以架构为中心：概要设计先确定六个包。
- 迭代与增量：按三个阶段实现。
- 所处阶段：细化阶段，需求和架构已基本确定，尚未进入构建。
- 五个工作流的产物：需求 → 用例图和用例规约；分析 → 类图、时序图、状态图；设计 → 概要设计说明书；实现 → 代码原型；测试 → 自动化测试和概要设计中的验证场景。

**问：什么是任务集裁剪，你们怎样裁剪？**
完整需求共定义 69 个功能用例。课程实验版只保留六个基本用例，以及课程要求的 UML 分析模型：用例图、用例规约和活动图，类图，每个用例的时序图和两张状态图。五个框架活动都保留，只是减少了任务量和严格程度。

**问：按 CMM，你们处于哪一级？**
大约是第 2 级（可重复级）。我们有分工、Git、文档模板和评审，但还没有组织级的统一流程，也没有定量的过程数据。

**问：软件生存周期中，你们处于哪个阶段？**
问题定义对应选题介绍；可行性研究对应学期项目约束和技术选型；需求分析对应需求规格说明书；软件设计对应概要设计，目前处于这一阶段；编码和测试处于原型阶段；运行维护尚未开始。

**问：你们用了敏捷开发吗？**
没有严格使用 Scrum 或 XP，但借鉴了部分做法：用户需求用“用户可以……”的句式描述，类似用户故事；按分支开发、小步提交，再经 PR 合并。

## 7 软件与质量

**问：软件由程序、数据和文档组成，分别对应什么？**
- 程序：知织桌面应用
- 数据：工作区（数据库、PDF 附件）、应用配置、日志
- 文档：用户需求、需求规格说明书、概要设计说明书、README、答辩材料

**问：知织属于哪类软件？**
应用软件，是面向个人用户的桌面工具。

**问：软件质量的几个方面分别对应什么？**

| 质量 | 项目中的对应 |
| --- | --- |
| 产品质量（外部） | 功能完整；冷启动不超过 5 秒；显示“已保存”等状态，便于使用 |
| 产品质量（内部） | 六个包分层、单向依赖，便于维护 |
| 过程质量 | 使用文档模板、开展评审、用 Git 管理版本 |
| 商业质量 | 课程开源项目不以盈利为目标；收益可理解为节省学生查找和整理资料的时间 |

**问：软件退化和软件危机在项目中怎样体现、怎样应对？**
退化来自多次变更且缺乏控制。项目早期也出现了需求不明确、变更频繁的情况，规格说明书经历了多个版本。应对方法：
- 规范过程：需求编号、评审、版本管理。
- 跟踪偏差：概要设计专门列出“当前实现与目标设计的差异”。
- 控制数据库结构变更：使用版本化迁移，已发布的迁移不再改写。
- 使用成熟的方法和工具：UML、分层架构、Git、draw.io。
